# 디자인·전체 흐름 검수 메모

## 검수 기준

`DESIGN.md`의 Warm Technical Editorial 토큰과 화면 계약을 기준으로 실제 운영 화면을 읽습니다. 이 문서는 “예쁘다”는 인상평이 아니라, 캡처에서 확인할 수 있는 정보 구조·신뢰 상태·상호작용을 기록하는 문서입니다.

## 1. 화면별 확인 결과

### 원본 인박스

실제 45건이 고밀도 표로 표시되고, 각 행에 처리 이유·권리·수집 상태·readiness·마지막 동기화·다음 작업이 함께 있습니다. `계획 만들기`, `검토 계속`, `지금 동기화`, `수집 재시도`는 실제 링크/폼으로 확인됩니다. 긴 표는 운영 큐로서 의도된 밀도입니다. 검수 시에는 제목 열의 가독성과 행 단위 다음 작업의 우선순위를 확인합니다.

### 원본 상세

현재 스냅샷 버전과 원문, readiness 누락, 권리 상태, Content Atom 위치, 연결된 결과물이 같은 화면에 있습니다. 원본 상세에서 계획으로 이동하는 주 행동과, 원문 근거가 없는 경우의 차단 문구를 구분해 확인합니다.

### Planner

Planner는 원본에서 자동으로 읽은 공통 맥락과 Solar 기본 Provider를 보여주고, 채널을 자동 선택하지 않습니다. 캡처에는 Instagram Carousel/Reels, Naver Blog Draft, Newsletter, TikTok Video, WordPress Article, YouTube Shorts가 각 목적·구조·검사 기준을 가진 선택 카드로 표시됩니다. 즉 채널 수가 한 개의 길이 변형으로 축약되지 않았는지, 선택하지 않은 출력이 계획 화면에서 생성되지 않는다는 설명이 유지되는지를 검수합니다.

### 실행 기록

run 상태, 결과물 상태, 실패 사유, retry Provider, Review Workbench 링크, Markdown/WordPress export 기록이 같은 운영 표면에 있습니다. 실패한 실행과 이전 결과 보존 문구가 성공 상태와 혼합되지 않는지 확인합니다.

### 설정

Solar Provider의 endpoint/model과 암호화된 키 저장 상태가 보이며 비밀값 자체는 노출되지 않습니다. 채널 카탈로그 활성화, Creator Identity 근거 사실, Voice, Audience Persona가 각각 별도 그룹입니다. 검수 포인트는 사실 입력에 근거 URL/설명이 필수인지, 채널 활성화가 Planner에 실제 반영되는지입니다.

### Review Workbench

데스크톱은 Source & Evidence / Structured Artifact / Preview·Checks·Versions·Run의 3-pane 구조입니다. 선택된 블록과 원본 위치가 동기화되고, 자동 품질 평가와 사람 원본 대조가 별도 상태로 표시됩니다.

`07_review_checks_queue.png`에서는 현재 원본 스냅샷과 직접 대조하지 않은 사실 블록 11건이 실제 큐로 표시되고, 승인 버튼은 비활성화되어 있습니다. 이는 모델 평가가 사람 확인을 대신하지 않는다는 Product Truth가 화면에 드러난 상태입니다. 큐의 “다음 미확인 사실 블록 검토”와 개별 `사실 블록 n` 버튼은 선택 상태를 바꾸는 실제 컨트롤입니다.

`08_review_versions.png`와 `09_review_run.png`는 승인/내보내기 이력과 생성 실행의 Pipeline·Prompt·Evaluator·보증 수준을 분리해 보여줍니다. 검수 시 이력 항목이 현재 상태 배지와 섞이지 않는지 확인합니다.

### 모바일 Review

모바일은 `원본 / 편집 / 검토` 탭을 사용하고 승인 액션을 sticky로 유지합니다. `08_review_check_queue.png`에서 44px 이상 터치 컨트롤, 사람 대조 큐, 자동 품질과 승인 차단을 한 흐름으로 확인할 수 있습니다. 첫 화면에서 큐를 지나치지 않는지, sticky 영역이 큐의 텍스트/버튼을 가리지 않는지는 사람 검수에서 특히 확인할 항목입니다.

## 2. DESIGN.md 정합성 체크

| 항목 | 캡처에서 확인한 근거 | 사람 검수 포인트 |
|---|---|---|
| 한국어 우선·단일 내비게이션 | 모든 운영 화면의 한국어 제목과 좌측 단일 사이드바 | 화면 폭이 줄어도 두 번째 workflow 내비게이션이 생기지 않는지 |
| Warm neutral 표면 | 크림색 canvas, 흰 surface, 어두운 sidebar, 제한된 red accent | accent가 위험/agent 상태와 혼용되지 않는지 |
| 고밀도 운영 화면 | Inbox/Runs의 표·행 단위 상태와 다음 작업 | 작은 글씨로 정보를 압축하지 않았는지 |
| 증거 상태 분리 | `확인 필요`, 자동 품질 평가, 사람 원본 대조, 승인 차단 문구 | 색상만으로 상태를 전달하지 않는지 |
| 실제 컨트롤 | 3개 입력 dialog, Review 4개 context tab, 모바일 3개 workbench tab | 클릭 시 내용이 바뀌고 비활성 버튼이 이유를 설명하는지 |
| 채널 구조 | Planner의 플랫폼별 목적·필드·검사 기준, Review의 Naver 미리보기 | Naver/Short 결과가 길이만 다른 동일 구조가 아닌지 |
| 점진적 공개 | Planner 공통 맥락 후 채널 카드, Settings의 그룹화 | 고급 설정이 첫 화면을 압도하지 않는지 |
| 승인 경계 | Review의 11건 큐와 비활성 승인, export 컨트롤 | 자동 평가 완료를 사람 승인 완료로 오인하지 않는지 |

## 3. 이번 캡처에서 반드시 확인할 위험

1. Inbox와 Planner는 의도적으로 긴 전체 페이지입니다. 실제 운영에서는 첫 viewport에서 검색/필터/다음 행동이 보이는지와, 세로 이동 후 행/카드의 제목이 유지되는지를 확인해야 합니다.
2. Review 모바일의 sticky 승인 영역은 안전 경계를 위해 고정되어 있습니다. 대조 대기 항목을 스크롤할 때 콘텐츠를 가리지 않는지 손가락으로 확인해야 합니다.
3. 채널 카탈로그가 많아질 때 Planner 카드의 순서와 한 화면의 인지 부하가 커질 수 있습니다. 현재 캡처는 실제 활성 Profile만 포함하므로, 채널 추가 시 동일한 구조 계약을 유지하는지 확인합니다.
4. 외부 WordPress draft와 실제 플랫폼 표시 결과는 자격증명/플랫폼 계정이 있어야 검수할 수 있습니다. 이 패키지는 해당 경계를 숨기지 않고, 승인 이후 export 조작 위치까지를 검수합니다.

## 4. 접근성·브라우저·운영 증거

- 이번 캡처는 Chromium headless에서 실제 서비스 주소 `192.168.50.130:3000`으로 수행했습니다.
- `tests/e2e.test.js`의 데스크톱/모바일 접근성 스캔은 이 UI 변경 기준으로 통과한 상태입니다. 대화상자·탭·폼은 실제 DOM 컨트롤로 캡처했습니다.
- 외부 브라우저 자동화 없이 OSAU 웹 앱 자체만 조작했습니다. RSS/WordPress/Naver 플랫폼의 비공식 자동화는 수행하지 않았습니다.
- 캡처 작업 자체는 POST/PUT/DELETE를 호출하지 않았고, DB·artifact·verification 상태를 변경하지 않았습니다.
